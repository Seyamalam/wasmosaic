# Next API priorities

## Recommendation

The initial ten families below now have working implementations, recorded as partial where their contracts are incomplete. The next checkpoint, `matchTemplate`, also has all six U8/F32 methods and optional masks. See [the parity ledger](PARITY.md#template-matching-differential-coverage) for its remaining numerical and alias differences.

Continue with `approxPolyDP` and `findContours` hole/tree hierarchy to strengthen shape analysis, then `warpPerspective` and the remaining `getPerspectiveTransform` contract for document rectification. Template matching's scalar benchmark is also a measured optimization candidate; the initial direct window scan is slower than the pinned baseline. The table below preserves the initial batch's dependency order and expansion goals.

Implement the following ten OpenCV.js-compatible API families in order. This is a product/engineering ranking, not a claim based on download or call-frequency telemetry: OpenCV publishes no such usage data. “Common” below is inferred from the workflows given first-class coverage in the official OpenCV.js image-processing tutorials and from how often one operation is a prerequisite for later workflows. The stock OpenCV.js 4.13.0 selector confirms that every named family is in the browser build ([binding configuration](https://github.com/opencv/opencv/blob/4.13.0/platforms/js/opencv_js.config.py)); the repository ledger remains the authority for WASMosaic status ([parity manifest](parity.json)).

## Delivery batches

1. **Browser image basics:** ranks 1–3. Promote each family only after the full selected OpenCV.js overload/type contract is covered; a useful code or interpolation slice remains `partial` under the project policy.
2. **Neighborhood-kernel foundation:** ranks 4–6. Share border lookup, separable convolution, accumulation depth, rounding, saturation, destination replacement, ROI, and alias handling.
3. **Complete analysis workflows:** ranks 7–8. The intended path is RGBA → gray → blur/threshold or Canny → contours → the contour geometry already shipped.
4. **Geometry and enhancement:** ranks 9–10. Reuse the resize sampler for warps and the threshold histogram/LUT machinery for equalization.

For each rank, first freeze the actual OpenCV.js 4.13.0 overload/arity and error behavior with the browser differential harness; Doxygen’s C++ defaults alone do not establish the generated JavaScript contract. Ship the portable scalar Rust implementation before considering SIMD, threads, or GPU acceleration, and optimize only against the repository’s browser benchmark process.

## Defer

- **DNN loaders/execution and model-backed face/object detectors:** model parsing, tensor planning, and large model assets are a separate platform investment and do not help the basic image pipeline.
- **Cascade, QR/barcode, ArUco/ChArUco, and calibration/PnP:** high user value, but they sit above still-missing image kernels, vector containers, drawing, model loading, or numerical solvers.
- **ORB/AKAZE/KAZE/BRISK detection and descriptors:** the configuration handles do not yet have gradient, pyramid, keypoint-vector, and descriptor kernels; finish the shared foundations before algorithm-specific work.
- **Optical flow, background subtraction, GrabCut, watershed, Hough transforms, and line-segment detection:** these are multi-stage algorithms whose prerequisites overlap with the ranked filtering, gradient, binary-mask, contour, and pyramid work.
- **Bilateral filtering, full cubic/Lanczos resampling, exhaustive color-conversion codes, and every morphology/border combination in the first slice:** retain the full-family target, but do not let long-tail variants delay a coherent browser workflow. Keep their ledger status `partial` until the complete selected family contract passes.
- **Further `matchTemplate` expansion:** the initial implementation now composes with `minMaxLoc` to locate templates ([Template Matching](https://docs.opencv.org/4.13.0/d8/dd1/tutorial_js_template_matching.html)). Use its browser benchmarks to choose optimization work, and retain partial status until the remaining alias, extreme-value, and error contracts are resolved.

## Re-ranking rule

Re-rank only when pinned-browser probes reveal a substantially larger contract than expected, a prerequisite remains blocked, or browser benchmarks show that a shared primitive is not viable. Do not use parity-family count alone: one complete dependency engine that enables several workflows is more valuable than several isolated configuration methods.
